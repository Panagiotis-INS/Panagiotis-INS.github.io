## Motivation:

Every vendor, every blog post, every LinkedIn thought-leader is throwing the same handful of words around (*model*, *agent*, *orchestrator*, *MCP*) and half the time they mean different things depending on who's talking.

This post is the glossary I wish I had when I started building AI-adjacent tooling for red team work. No hype, no "the future of…" filler. Just what the terms mean, where they overlap, and where people confuse them.

If you already know this stuff, skip it. If you don't, this is the base you need before any of the follow-up posts make sense.

## The Core Terms:

### Model

A **model** is the trained artifact: weights sitting in a file (`.safetensors`, `.gguf`, whatever). It's a big pile of numbers that, given an input, produces an output. Nothing more.

A model on disk does nothing on its own. It needs something to load it into memory, feed it tokens, and read tokens back. "Model" is the *thing*, not the *system*.

You'll hear people say "we're using the Claude model" or "the Llama 3 model." They mean the specific weights + architecture combination.

### LLM

An **LLM** (Large Language Model) is a *type* of model. Specifically: a transformer-based model trained on massive text corpora to predict the next token given a sequence of previous tokens.

Every LLM is a model. Not every model is an LLM. Stable Diffusion is a model but not an LLM. Whisper is a model but not an LLM. GPT-4, Claude, Llama, Gemini, DeepSeek are all LLMs.

**Common confusion:** People use "model" and "LLM" interchangeably in casual writing. In this space, when someone says "the model," 90% of the time they mean the LLM. But when it matters, for example when you're mixing an LLM with a vision model or an embedding model in the same pipeline, you need to be precise.

### Harness

A **harness** is the runtime environment that wraps a model and makes it actually usable. It handles:

- Loading the weights
- Tokenization / detokenization
- Sampling parameters (temperature, top-p, etc.)
- Input/output plumbing
- Tool exposure to the model
- Safety filters, logging, telemetry

Think of the harness as the "shell" the model runs inside. Anthropic's Claude Code, Cursor, `llama.cpp`'s CLI, Ollama; all of these are harnesses to varying degrees. Even the OpenAI API is a harness (a hosted one).

An agent like Hermes or Agent Smith runs inside a purpose-built harness. The harness is what actually implements the tools the model is allowed to call.

### Orchestrator

An **orchestrator** is the layer that decides *what happens next*. It sequences model calls, routes outputs, and chains steps together.

Concretely, an orchestrator might:

1. Take a user request
2. Call an LLM to classify it
3. Based on the classification, call one of three different pipelines
4. Each pipeline calls other models, tools, or APIs in a specific order
5. Aggregate the results and return

LangGraph, LangChain, Haystack and Semantic Kernel are all orchestration frameworks. But you don't need a framework; a few hundred lines of Python is often enough.

#### Orchestrating Multiple Agents and Sub-Agents

Orchestration gets more interesting the moment you stop dealing with a single agent and start wiring several of them together. This is where a lot of production AI systems actually live.

Two patterns you'll see repeatedly:

**Supervisor / worker (a.k.a. "manager and crew"):** one top-level agent (the *supervisor*) receives the task and decides which specialised *worker agent* should handle each part. The supervisor doesn't do the work itself; it delegates, collects results, and decides when the goal is met. Think PM → Dev → QA → Tester → Reviewer, each one a separate agent with its own prompt, tools, and context window. The orchestrator is what routes messages between them and enforces the hand-off contract.

**Sub-agents (fan-out / recursive delegation):** a parent agent, mid-task, decides it needs help and spins up a *sub-agent* with a scoped goal, a smaller toolset, and its own fresh context. The sub-agent runs its own loop, returns a result, and dies. The parent continues. Anthropic's Claude Code, Cursor's background agents, and most "deep research" products work this way. It's how you keep a long-running task from drowning its own context window: you push detail work down into short-lived children and only surface their summaries back up.

Why do this instead of one big agent with everything?

- **Context isolation**: each agent gets a clean, focused window. No cross-contamination between unrelated subtasks.
- **Specialisation**: different agents can use different models (cheap model for triage, expensive one for the hard reasoning), different system prompts, different tool sets.
- **Parallelism**: independent sub-agents can run concurrently. One big loop can't.
- **Blast-radius control**: a sub-agent with only read tools can't accidentally break things a parent with write tools could.
- **Debuggability**: when something goes wrong, you can point at which agent screwed up instead of scrolling through a 200k-token single-agent transcript.

The orchestrator's job in a multi-agent setup is heavier than in the single-agent case. It defines *which* agents exist, *how* they talk to each other (message schema, hand-off protocol), *who* can spawn *whom*, and *when* the whole thing terminates. Get this wrong and you get infinite recursion, agents talking past each other, or a supervisor that never decides it's done.

**Harness vs orchestrator:** the harness *runs* the model. The orchestrator *decides which model (or which agent) to run, when, and with what inputs*. In small systems they collapse into the same code. In big multi-agent ones they're very much separate.

### Agent

An **agent** is what you get when you put an LLM inside a loop, give it tools, and let it decide the next step itself.

The pattern, stripped to the bone:

```
loop:
    action = LLM(context + goal)
    if action == "done": break
    result = execute(action)
    context += result
```

That's it. The distinguishing feature is that **the model chooses the next step**, not the surrounding code. That's the difference between an agent and an orchestrator: in an orchestrator, the *developer* wrote the flow. In an agent, the *model* decides the flow at runtime.

Everything else (memory, planning, sub-agents, reflection) is a variation on this loop.

**Agent vs chatbot:** a chatbot answers. An agent acts. A chatbot with tool calls starts blurring into agent territory; the line is fuzzy on purpose.

**Agent vs orchestrator:** deterministic flow = orchestrator. Model-decided flow = agent. Most production systems are a hybrid: an orchestrator that calls agents inside specific steps.

### Skill

A **skill** is a packaged capability the agent (or model) can invoke. The term is vendor-loaded. Anthropic uses "Skills" to mean a specific format (folder + `SKILL.md` + optional code) that Claude can discover and load on demand. OpenAI uses "GPTs" and "Assistants" for a similar concept.

Generically, a skill is: *a named bundle of instructions, prompts, and optionally code, that teaches the model how to do one specific thing well*.

**Skill vs tool:** a tool is a single callable function the model can invoke (`read_file`, `run_bof`). A skill is bigger; it's a *how-to*, often combining multiple tools, prompts, and reference material. "Grep this codebase" is a tool. "Perform a source-code security review" is a skill.

**Skill vs prompt:** a prompt is text you send in. A skill is a reusable, versioned, discoverable package the harness can pull into context when relevant.

### MCP

**MCP** (Model Context Protocol) is an open protocol, originally from Anthropic and now broadly adopted, that standardizes how models talk to external tools and data sources.

Before MCP, every harness invented its own way to expose tools to the model. That meant every tool integration was bespoke. MCP defines a client/server protocol so any MCP-compatible harness can plug into any MCP server and get:

- A list of available tools
- A list of available resources (files, DB rows, etc.)
- A list of available prompts

Then the model can call them uniformly.

**MCP vs tool:** MCP is the *protocol*. A tool is a *thing* exposed over that protocol (or any other). MCP is USB-C for LLM tooling.

**MCP vs skill:** skills are packaged behaviors loaded into the model's context. MCP servers are external processes the model reaches out to over a wire protocol. A skill might *use* an MCP server; they operate at different layers.

## Concepts People Confuse:

Quick reference for the ones that trip everyone up:

| A | vs | B | Difference |
|---|---|---|---|
| Model | LLM | LLM is a subtype (text, transformer) of model |
| Harness | Orchestrator | Harness runs the model; orchestrator decides the flow |
| Orchestrator | Agent | Deterministic flow vs model-decided flow |
| Tool | Skill | Single callable vs packaged how-to |
| Skill | MCP server | Loaded into context vs called over a protocol |
| Prompt | Context | The instruction you write vs everything in the window |
| Chatbot | Agent | Responds vs acts |

## The "Engineering" Flavors:

Once the vocabulary is straight, the practice around it splits into a few disciplines. These aren't officially standardized; they're terms the field converged on because the problems are real.

### Prompt Engineering

The oldest of the three. **Prompt engineering** is the craft of writing the input string that makes a model give you what you want.

This includes:

- Role/persona framing ("You are a senior red team operator…")
- Format constraints ("Respond in JSON with keys `x` and `y`")
- Few-shot examples
- Chain-of-thought triggers ("Think step by step")
- Guardrails and refusal-avoidance in either direction

It's the most visible and the most overrated. It matters, but people spend weeks perfecting a prompt when the actual problem is that the model doesn't have the right information, which is a context engineering problem, not a prompt problem.

### Context Engineering

**Context engineering** is designing *what enters the model's context window*, in what order, and how it's compressed when it gets too big.

The context window is limited. Even models with a million tokens degrade in the middle. So context engineering deals with:

- **Retrieval**: RAG, embeddings, vector search, pulling in the relevant chunks
- **Ordering**: what goes at the top of context, what goes at the bottom (recency bias is real)
- **Compaction**: summarizing older turns, dropping irrelevant tool output
- **Memory**: what persists across sessions, what doesn't
- **Isolation**: keeping untrusted content clearly separated so prompt injection doesn't hijack the model

This is where most agent quality comes from. Prompt engineering is 10% of the game once you're past a toy demo. Context engineering is the other 60%.

### Loop Engineering

**Loop engineering** is designing the agent's decision loop, the outer control structure that determines *how the agent thinks over time*.

Concerns include:

- **Step budgets**: max iterations before you cut it off
- **Reflection steps**: forcing the agent to critique its own plan before continuing
- **Retry logic**: what to do when a tool fails or returns garbage
- **Escalation**: when to ask the human, when to spawn a sub-agent
- **Termination conditions**: how does the agent know it's done?
- **Parallelism**: which steps can fan out, which must serialize
- **Cost/token guardrails**: kill switches before the bill explodes

Bad loop engineering is why so many agent demos fall apart on real tasks. The model is fine. The loop around it is a while-loop with no brakes.

### Others You'll Hear:

- **Eval engineering**: designing the test harness that tells you if a change made the system better or worse. Underrated. If you can't measure it, you're guessing.
- **Workflow engineering**: the orchestrator side. Designing deterministic pipelines of model calls. Sometimes used interchangeably with orchestration.
- **Tool engineering**: designing tools that the model actually uses well. Turns out models are picky. Bad tool names, verbose outputs, and ambiguous parameters wreck agent performance.
- **RAG engineering**: a subset of context engineering focused specifically on retrieval-augmented generation systems.

## How It All Fits Together:

A concrete stack, bottom to top:

1. **Model**: the weights (e.g. Claude Sonnet 4).
2. **Harness**: the runtime that loads/serves the model and exposes tools to it.
3. **Tools / MCP servers**: the things the model can call.
4. **Skills**: packaged how-tos the model can pull in when relevant.
5. **Agent loop**: the control flow that lets the model decide the next step.
6. **Orchestrator**: the outer layer that composes agents, sub-agents, tools, and deterministic pipelines into a product. In multi-agent systems this is also where supervisor/worker routing and sub-agent spawning rules live.

Prompt engineering, context engineering, and loop engineering are the disciplines you apply *across* those layers to make the whole thing work.

## Closing:

You'll see these terms used loosely in the wild. That's fine; language is messy. But when you're actually building something, being precise about which layer you're touching saves days of debugging.
